## 1. Tóm tắt

- Mục tiêu: footer sống động theo ảnh tham chiếu, nội dung chính lấy DB và link có thể quản trị.
- In: danh mục, bài viết, chi nhánh, policy/support links; CRUD admin; cache/error/empty state.
- Out: sửa nội dung các trang legal, newsletter, social integrations, thay đổi toàn bộ site shell.
- Approach: reuse `Product`, `CommunityPost`, `Branch`; thêm `FooterLink` cho chính sách/tư vấn; admin manage ở `/admin`.
- Rủi ro: schema cần được push khi triển khai; giảm thiểu bằng migration instructions/backup/rollback, không tự chạy production mutation.
- AC quan trọng: public chỉ render dữ liệu active/giới hạn; không ADMIN không thể quản lý; link không thể điều hướng ra protocol/external origin.

## 2. Bối cảnh và mục tiêu

Khách truy cập site thường dùng footer để tìm nhóm sản phẩm, nội dung hướng dẫn, policy, tư vấn và địa điểm. Admin cập nhật các link hỗ trợ/chính sách. KPI định lượng không được cung cấp; nghiệm thu theo destination, nguồn DB, state và responsive acceptance.

## 7. Functional requirements

- Must: render active branches (max 5), distinct active product categories, latest community articles (max 4), active policy/support links (max 8 per section).
- Must: database link groups are manageable by ADMIN with search/pagination and create/update/active toggle/delete.
- Must: validate internal href, label length, section, sort order; deny non-admin at API/action boundary.
- Must: empty/DB failure does not fail page rendering; cache DB results and invalidate after link mutation.
- Should: default seed for legal/support routes on fresh DB; avoid overwriting admin edits on repeated seed.
- Won’t: newsletter submission or fake social links.

## 8. NFR

- Bounded read queries; use 5-minute cache and cache tag invalidation.
- Public links cannot contain external/protocol-relative URL; admin mutation requires server authorization.
- SSR DB failure is logged without exposing raw connection details and renders safe empty/error footer.
- Existing routes/API remain compatible.

## 9. Quyền và trạng thái

- Public actor: read-only active data.
- ADMIN: read/create/update/activate/deactivate/delete links.
- Other/anonymous: API 403; server action throws existing authorization error.
- Validation errors before write; missing record returns not found/error; DB exception no cache invalidation.

## 9A. Domain State Machine Contract

```text
Stateful scope: YES
Reason: FooterLink active state changes public visibility; CRUD writes authoritative DB data.
State owner: Prisma FooterLink; mutation boundary app/actions/admin.ts; authorization auth()/Role.ADMIN.

OBJECT       STATE            SOURCE          OWNER                 INITIAL       TERMINAL
FooterLink   active/inactive  PostgreSQL      ADMIN server action   active        deleted
```

Invariants: only ADMIN mutates; group belongs to POLICY/SUPPORT; href is safe internal route; public query only active; successful writes invalidate `site-footer`; failed writes do not.

```text
TR-ID               FROM          COMMAND       GUARD / FAILURE                 RESULT / TEST
TR-FOOTERLINK-01    absent        create        ADMIN + valid; duplicate/error  active; schema/guard test
TR-FOOTERLINK-02    existing      update        ADMIN + valid; missing/error    saved; validation/not-found test
TR-FOOTERLINK-03    active        deactivate    ADMIN; missing/error            hidden publicly; state test
TR-FOOTERLINK-04    inactive      activate      ADMIN; missing/error            visible publicly; state test
TR-FOOTERLINK-05    existing      delete        ADMIN; missing/error             absent; state/guard test
```

Writes are single-row Prisma operations; no external side effects. Cache invalidation follows successful write. Concurrent edits are last-write-wins as existing admin CRUD; this content has low conflict impact.

## 10. Data model

Add `FooterLink` with id, section enum (`POLICY`, `SUPPORT`), label, href, sortOrder, active, createdAt, updatedAt; indexed by section/active/sortOrder; unique section+label. Existing Product/Branch/CommunityPost remain authoritative for respective dynamic groups. Additive schema push; rollback requires backup and removal of the additive table/model only after code rollback.

## 11. API/integrations

Admin GET `/api/admin/footer-links?page&pageSize&q&section`: ADMIN-only, bounded page size, items/total/pages. CRUD via guarded server actions. Public footer has no new public API; SSR reads Prisma.

## 12. UI behavior

See UX report; mobile wrapping, empty/loading/pending/error admin states, active status, details, and destination checks.

## 13. Edge/failure cases

DB unavailable/empty, inactive branch/category/link, duplicate section+label, malformed/external href, page out of range, missing id, concurrent update, cache invalidation only after success.

## 14. Acceptance criteria

- Footer queries database-backed groups and article route/category map destinations correctly.
- Admin CRUD and all API reads enforce `Role.ADMIN`; invalid input creates no writes.
- Query bounds and ordering hold; inactive links never public-render.
- UI responsive at 390/768/1440; empty/error layouts remain stable.
- `npx prisma validate`, `npx prisma generate`, TypeScript, ESLint/build pass or inherited warnings are partitioned.

## 15. Options/tradeoffs

Selected: extend current DB models for branches/products/posts and add one manageable FooterLink model. Avoids duplicating existing content or requiring manual SQL for routine footer edits.

- Do not implement unsupported newsletter/social controls.

## 20. Deep thinking

- 10x posts/branches: footer reads fixed maxima and distinct category count; avoids loading all posts/branches.
- Misuse: admin can set hostile URL or too-long label; reject unsafe href/length and containment-break values.
- Essential Must: DB-sourced sections and server-side admin guard; static link fallback would violate requested source-of-truth.
- Side effects: root layout cache and article/product routing; explicitly invalidate shared tag, use existing routes.
- Data migration: additive table via existing db push workflow; backup/rollback plan required.
- Permissions: existing ADMIN role is sufficient; no new role/feature access.
- Concurrency: last-write-wins; no multi-object transaction/external side effects.
- Consistency: Prisma singleton, server actions, AdminDashboard tabs, Lucide/Tailwind.
- Proactive proposal (non-binding): add a future public subscription workflow only after consent, unsubscribe, and storage requirements are defined; excluded now.
- Feature flag: unnecessary for a simple additive public footer; rollback via code + additive table preservation/drop after backup.
